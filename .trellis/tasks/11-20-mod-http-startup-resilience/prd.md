# 恢复本机 API，并隔离监听启动失败

## 目标

在隔离实机上复现 Windows 的「句柄无效」后，Mod 能自行恢复本机 HTTP API。玩家不用改代理、Windows 设置或另装运行时；恢复后 MCP 与 Mod 双开仍可使用。若恢复也失败，主窗口仍保留不依赖 API 的单人功能。

## 已确认的证据

- 游戏 v0.113.1 跑到 [Mod 启动入口](../../../STS2AIAgent/ModEntry.cs) 后，Windows `HttpListener.Start()` 报 native error 6，原入口因此没走完。
- 同一个最小程序，`.NET 9.0.20` 下直接运行生成的 EXE 连续报 error 6；`dotnet` 加载同一 DLL 成功，同端口的普通回环 TCP 监听也成功。因此不能归咎于所有 .NET 9，也没有证据归咎于代理。
- 同一测试 EXE 里 `HttpListener` 报 error 6 后，走普通回环 TCP 的 Kestrel 能启动并让一个真实 HTTP 客户端读到测试 `/health`，连续复测通过。这个探针没有加载游戏；能否随 Mod 打包并在游戏进程内加载仍要实证。

## 要求与验收

| 要求 | 可观察的验收 |
| --- | --- |
| API 真恢复 | 默认先用现有监听；Windows error 6 时同一个 Mod 自行启用回环 HTTP 后备。用 v0.113.1 隔离游戏和正式产物布局复现原错误，实际读取 `/health` 和 `/state`；不能只用模拟服务器或面板截图代替。 |
| 保持调用兼容 | 不改变 HTTP、SSE、原生 MCP 和 Python sidecar 契约，不改变默认与固定端口策略。仍只监听回环；Host/Origin 校验、队友令牌和请求限制在两条路径上都生效。使用官方构建或系统已配好的运行时之外，不增加玩家手动安装步骤。 |
| 验证受影响的联机链路 | 无模型 Key 的隔离双开，主窗和队友都到 `/health` 就绪，进入同一局，队友 `/mcp` 通过原生 MCP 至少执行一次 `act` 出牌；DSH 客户端实测单列，不把直测算成 DSH。 |
| 两种监听都失败时只降级主窗 | 主窗单人入口与悬浮窗仍可用；MCP、复制地址、邀请和续局给出原因而不误报就绪、不启动子进程、不清空已保存偏好。队友子进程双失败走现有启动失败上报。 |

## 范围外

不修改系统代理、Windows 服务、防火墙、游戏运行时和正式安装；不为普通端口占用绕过固定端口策略；不调用付费模型，不自动发版或更新工坊。找出具体哪个 Windows 调用或进程条件产生错误 6 不是发布代码的前置条件；不能把未验证的底层原因写成结论。
